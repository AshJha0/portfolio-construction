# Contributing

`portopt` is one library written four times: a Python reference and ports
in C++26, Rust and Java 25. The four agree because each implements the same
pinned contract in [API_SPEC.md](API_SPEC.md) and each test suite checks
the same golden file, `data/golden/golden.json`. A change is finished when
all four suites pass in CI (`.github/workflows/ci.yml`) on Linux, Windows
and macOS.

## Build and test each port

All commands run from the repository root unless a `cd` is shown.

| Port | Toolchain | Build and test |
|---|---|---|
| Python | 3.11 or later (CI: 3.11 and 3.13) | `python -m pip install -e "python[dev]"`, then `pytest -q python`; lint with `ruff check .` and `ruff format --check .`; types with `mypy` from `python/` |
| C++ | C++26, CMake 3.25 or later; GCC 14, Clang or MSVC (`/std:c++latest`) | `cmake -S cpp -B cpp/build -DCMAKE_BUILD_TYPE=Release`, `cmake --build cpp/build --config Release --parallel`, `ctest --test-dir cpp/build -C Release --output-on-failure` |
| Rust | stable; the minimum version is `rust-version` in `rust/Cargo.toml` | `cd rust`, `cargo test --release` |
| Java | JDK 25, Maven | `cd java`, `mvn -B verify` |

GoogleTest is used from the system when CMake finds it and fetched
otherwise, so a fresh machine needs only CMake and a compiler.

The demos are the quickest end-to-end check, and CI diffs their output
across languages:

```bash
python python/demo.py
(cd cpp && ./build/portopt_demo)      # Windows: build\Release\portopt_demo.exe
(cd rust && cargo run --release --bin demo)
(cd java && mvn -B -q exec:java)
```

## The golden-file rule

`data/golden/golden.json` and the files beside it in `data/` are written by
`data/generate_data.py`. **Never edit them by hand.** To change a golden
value, change the generator or the Python reference, then run:

```bash
python -m pip install -e "python[dev]"   # the generator needs scipy for its checks
python data/generate_data.py
```

The generator draws the synthetic returns with `numpy.random.default_rng(42)`,
re-reads the CSV as written, computes every case with the Python
reference, and checks the reference against independent computations
(`numpy.linalg.lstsq`, a transcription of `covCor.m`, scipy SLSQP, the ERC
identity, the Black-Litterman limits) before it writes anything. Running it
twice must give byte-identical files; check with `git diff --stat data/`.

Commit the regenerated files in the same change as the code that caused
them, and say in the pull request why the values moved.

## The API_SPEC contract

`API_SPEC.md` pins every numerical algorithm: the Cholesky variant and its
pivot gate, the projection breakpoint scan, the active-set QP and its KKT
certificate, the coordinate-descent update, the Ledoit-Wolf sums term by
term, summation order, tolerances and iteration caps. Anything a port could
reasonably do differently is pinned there, because otherwise the goldens
would agree only to iteration-path accuracy rather than to rounding.

If a change alters behaviour, change `API_SPEC.md` first, then the Python
reference, then the generator and goldens, then the three ports.

## Parity checklist

Use this for any change that touches numerics.

- [ ] `API_SPEC.md` describes the new behaviour, including error messages
      that name the offending argument.
- [ ] Python reference implemented and exported from
      `python/src/portopt/__init__.py` (and `__all__`).
- [ ] Goldens regenerated by `data/generate_data.py`, never hand-edited,
      and byte-identical on a second run.
- [ ] C++: header in `cpp/include/portopt/`, source in `cpp/src/`, both
      listed in `cpp/CMakeLists.txt`; tests in `cpp/tests/`.
- [ ] Rust: module exported from `rust/src/lib.rs`; tests in `rust/tests/`.
- [ ] Java: public class in `com.quant.portopt`; Maven finds new sources and
      `*Test` classes on its own.
- [ ] Each suite asserts the exact golden case count, so a new case fails
      every port until it is handled.
- [ ] All four demos still print the same numbers.
- [ ] `CHANGELOG.md` entry under `[Unreleased]`; README, LEARN.md and
      COOKBOOK.md updated where they mention the changed behaviour.

## Pull requests

Keep commits small, each saying what changed and why. The pull request
template lists the checks a reviewer expects. Run all four suites locally
before pushing.

## Writing style

The docs have two readers: a student meeting the ideas for the first time
and an experienced reviewer checking the claims. Give the plain idea
first, then the formal statement, then a small worked example. Every
factual statement names the file, test or command behind it. Write in the
first person plural, keep paragraphs short, and do not claim anything a
test or a reference does not back.
